# Scanner builder: current implementation audit

September 28, 2026. This is a local code and test audit for discussion before implementation. It covers the builder, scanner settings, fictional findings, local workspace, current checker coverage, and the earlier scanner research. No browser interaction, live X request, or user-data inspection was performed. The only file created is this report; application files and browser storage were left unchanged.

The central finding is that the builder saves a scanner configuration, but it does not run that configuration against live posts or tokens. Only the selected scanner family changes which fictional examples appear. The X setup also has a naming mismatch, permissive account completion, and a concrete separator-only validation bug. These are separate issues from the substantial work required to connect an actual X scanner.

The form asks for a name before showing its “Find” choices: “Public figures,” “New projects,” and “All coins.” The X-specific fields appear only after choosing “Public figures.” Creating another new scanner uses the same suggested name; saving custom scanners does not require unique names. **Usability hypotheses to discuss, not findings from user testing**

- A user thinking “scan X accounts” may not map that intent to “Public figures,” especially after generic Create opens a project scanner.
- Asking for a name before purpose/accounts may impose an unnecessary first decision; repeatedly suggesting “My first scanner” may make later retrieval harder.
- “Use scanner,” Active placement, and New badges can communicate operational readiness more strongly than the later preview disclaimer, particularly when no account has been selected.
- The number and ordering of technical options may make account setup look like a trading-filter task. Hidden configured constraints may be hard to remember after returning to an edit.
- A checker that accepts eight networks may create an expectation that scanners share that coverage. No network promise should be inferred until product scope and integrations are decided.

**Small conceptual fixes, in discussion order**

1. Agree on the scanner’s present and intended job: saved preview configuration today; explicit X monitoring and token matching only after an integration exists. Decide supported networks and direct-versus-theme expectations before changing the UI.
2. Use one clear X-facing name consistently across discovery, Create, type selection, review, and saved details. Consider choosing purpose first, then accounts, with an editable suggested name afterward. Preserve an explicitly edited user name when changing type.
3. Define account completion separately from draft saving. Normalize parsed handles, handle separator-only input, and decide whether to accept profile URLs. Keep existence verification distinct from syntax checking. An unfinished account configuration should remain easy to save without suggesting it is actively monitoring.
4. Keep People/accounts, Matches, and Posts together for an X scanner. Offer a small basic filter set and move detailed market/ownership controls behind a consistent optional section; surface a compact indication when hidden constraints are set.
5. Preserve the existing draft/review/recovery safeguards and update destination copy to Profile. State plainly what will be saved and what will actually affect results; avoid implying that placeholder examples validate a chosen configuration.

These are discussion proposals only. No application change has been made.
